# A04 — индивидуальные AWG-ключи и работающий worker на Brain

На Brain опубликован backend `d3eba8945e74eca025e2a8589be110d070fb562d`
(PR #245). Общие ключи owned AWG2/AWG3.1 заменены индивидуальными;
постоянный worker включён и дал три последовательных отчёта без ошибок.
Это закрывает миграцию прежних shared peers и подтверждает работу планировщика
на текущем runtime. Полный A04, приёмка установленного текущего клиента и
публичный релиз остаются открыты.

[Receipt и hashes](evidence/a04-production-migration-20260909/receipt.json)
связывают команды, исходники, наблюдения и сохранённые ошибки.

## Изменение ключей

- Для двух допустимых owned установок выпущены четыре разных ключа: по одному
  на установку и протокол. L3 action-intent PUT и последующее чтение подтвердили
  замену материала. Старые строки и зашифрованная история сохранены.
- На DE перед изменением сохранены исходные конфигурации в
  `/root/backups/r12-awg-migration-20260909/`. Публичные allowlists и права
  подписок не менялись; публичный AWG не включён.
- Текущий проход отозвал восемь неактуальных строк, отдельно отозваны две строки
  старого server record. После проверки отсутствия активных потребителей
  удалён один shared peer из файла и работающего интерфейса каждого протокола.
  Повторное удаление вернуло ноль изменений.
- Итоговое чтение DE: `pokrovawg2` и `pokrovawg31` активны, у каждого ровно два
  peer; сохранённые и работающие наборы совпадают с четырьмя новыми ключами.

## Проверка Core и доступа worker

Core `c7a11f7` имеет то же дерево, что опубликованный `7444e53`. Из его
неизменяемого Git snapshot собран Linux ARM64 oracle. На owned RU Pi четыре
новых ключа прошли authenticated egress; отдельная проверка подтвердила отказ
двух старых shared keys и успешную работу двух новых. Это восемь наблюдений
при MTU 1280, а не проверка установленного Android/Windows или полной MTU-матрицы.
Временный бинарник на Pi удалён; исходный бинарник и его hash сохранены локально.

Для Brain создан отдельный SSH-ключ без экспорта private material. На DE он
ограничен исходным адресом Brain и forced command текущего peer-removal helper.
Проверены отказ произвольной команде и идемпотентное удаление отсутствующего peer.
Host key закреплён через уже доверенный SSH-доступ. Старые authorized_keys сохранены.

## Сохранённые ошибки и границы

Первый запуск миграции остановился до записи конфигурации из-за отсутствующего
родительского backup-каталога. Исходная конфигурация не изменилась; исправлен
только подготовительный helper и выполнен успешный повторный запуск.
Оба результата сохранены. Часы current-origin и Brain не используются для
вывода общего порядка операций; зависимости команд заданы в сохранённых helpers.

Текущий Huawei возвращён и обновлён отдельным срезом, вход в существующую Windows
VM восстановлен. Их подключения с текущими сборками ещё не закрыты этим отчётом.
VM имеет собственную установку, отличную от мигрированной Windows: чужие ключи
ей не выдавались. Полные client/candidate, OIDC и release gates остаются открыты.

Проверки документации: `python -B -m pytest -p no:cacheprovider tests/test_agent_docs_contract.py tests/test_agent_context_packet_audit.py -q` — 33 PASS; `python -B scripts/agent_context_packet_audit.py --platform-context-root .` и `python -B docs/developer/work-orders/2026-09-05--consolidated-release-and-post12/validate_package.py` — PASS; `git diff --check` — PASS. После настройки BotFather владельцем провайдер открывает страницу входа для admin callback; реальный вход и step-up ожидают подтверждения в Telegram. [Новый readback](evidence/a04-production-migration-20260909/oidc-callback-after-owner.json).

Последующая [реальная OIDC-проверка](EXECUTION-OPERATOR-LIVE-2026-09-09.md) подтвердила вход и step-up одной сессии после действий владельца. Это отдельное доказательство; bootstrap metadata read выше сам по себе такого вывода не давал.
